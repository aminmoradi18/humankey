# Zetaris in HumanKey: the Unified Semantic Layer and what we learned

HumanKey's agents never read a database directly. Every fact they use comes from SQL that runs
through Zetaris and comes back with a receipt (the SQL, the sources it touched, the row count and a hash
of the result). This page covers the four steps (sources, USL, data quality, queries), then reflects on
what worked and what we would change.

## 1. Data sources

| Source | What it holds | How it is onboarded |
|---|---|---|
| `northwind_erp` | The company ERP: vendors, purchase orders, 12 months of payments, e-mails, bank-change requests, new invoices. Synthetic, generated by `data/gen.py`. | A PostgreSQL database registered with `CREATE DATASOURCE … jdbcdriver "org.postgresql.Driver"` and `REGISTER DATASOURCE TABLES`. |
| `GLEIF_REST` / `gleif.lei_entities` | The live public Legal Entity Identifier registry (CC0) for every LEI in our vendor master. | `CREATE LIGHTNING REST TABLE` on `api.gleif.org`, flattened with a SchemaStore view (`LATERAL VIEW explode(data)`). |

The vendors are real companies with their real LEIs; everything financial about them is synthetic.
Setup is one command: `python3 scripts/setup_zetaris.py` (DDL in `scripts/register_zetaris_sources.sql`
and `scripts/usl_northwind.sql`). It checks row counts against the CSVs it loaded.

## 2. The Unified Semantic Layer `lightning.metastore.humankey.northwind`

Six tables with primary and foreign keys, compiled in one `COMPILE USL … DEPLOY` statement:

```
vendors(vendor_id PK, …, lei, iban_hash, iban_last4, gleif_legal_name, gleif_entity_status, gleif_registration_status)
invoices(invoice_id PK, vendor_id FK -> vendors, po_id, amount, iban_hash, …)
payments(payment_id PK, vendor_id FK -> vendors, …)
purchase_orders(po_id PK, vendor_id FK -> vendors, …)
bank_change_requests(request_id PK, vendor_id FK -> vendors, new_iban_hash, verified_by, …)
emails(email_id PK, from_domain, subject, body, …)
```

`vendors` is where the two sources meet. It is activated as
`northwind_erp.vendors LEFT JOIN gleif.lei_entities ON lei`, so one table gives the agents a vendor's
bank account on file and its legal status in the public registry, with no join in the agents' code.

## 3. Data quality

| Rule | Table | Expression | Result on the demo data |
|---|---|---|---|
| `vendor_id` (FK) | invoices | declared in the model | 16 valid, **1 invalid** (INV0004: its vendor is not in the master) |
| `vendor_in_gleif` | vendors | `gleif_legal_name IS NOT NULL` | 12 valid, **1 invalid** (Kestrel: LEI unknown to GLEIF) |
| `vendor_lei_current` | vendors | `gleif_registration_status = 'ISSUED'` | 9 valid, 4 invalid (lapsed renewals; informational) |
| `bank_change_verified` | bank_change_requests | `verified_by IS NOT NULL AND length(verified_by) > 0` | 1 valid, **1 invalid** (an e-mailed change nobody called back) |
| `invoice_amount_positive` | invoices | `amount > 0` | 17 valid |
| `invoice_has_payee` | invoices | `iban_hash IS NOT NULL AND length(iban_hash) > 0` | 17 valid |

The foreign-key rule matters most in our product. The agents' work list joins invoices to vendors
(that is how they get vendor data), and an inner join drops an invoice whose vendor is missing without
any error. So every run asks Zetaris itself: `RUN DQ vendor_id TABLE …invoices` and
`SHOW DQ INVALID RECORD vendor_id TABLE …invoices`. The invalid records are exactly the invoices the
agents never saw. That number goes to the hardware key, which shows "1 of 17 NOT checked" and signs
it into the approval. A gap cannot hide behind a clean-looking report.

## 4. Queries

All agent SQL goes through one function (`zetaris/client.py`). Reads return rows and a receipt;
anything that changes the instance needs a human approval on the key, and `INVALIDATE CACHE` is never
sent. Seven checks run per invoice (registry, account vs master and change requests, sender domain,
purchase order, amount history, split pattern, header), plus the coverage and data-quality queries once
per run. A full run of 17 invoices makes about 370 Zetaris queries; the critic re-runs each one and
compares result hashes before anything is approved.

## 5. A least-privilege identity for the agents

Following the permissions guide ("give each agent and application its own user", "separate building from
reading"), `scripts/zetaris_agent_user.py` sets up a non-administrator user `humankey-agent` in a role
`humankey_readonly` and then runs every check *as that user*, so the answers come from Zetaris and not
from our own write guard. Result on the local edition 2.4.3.1 (24 Oct):

| As the agent user | Expected | Zetaris |
|---|---|---|
| `SELECT` on the ERP datasource (granted) | allowed | allowed |
| `INSERT` into the ERP | refused | refused: "does not have privileges to execute 'INSERT'" |
| `CREATE LIGHTNING DATABASE` | refused | refused: "User is not permitted to run this command" |
| `SELECT` on a USL table (granted) | allowed | **refused**: "does not have access to USL: `metastore`.`humankey`.invoices" |
| `RUN DQ` on a USL table (granted) | allowed | **refused**, same message |

Denied by default, and the write refusals are exactly what we want: defence in depth behind our own guard.
The USL grant is the gap. We granted `SELECT ON USL NAMESPACE lightning.metastore.humankey.northwind`, on
`lightning.metastore.humankey`, and on the single table, to the role and to the user, and ticked View on
Unified Semantic Layer under Management > Permissions. `SHOW GRANT` lists all of them, yet the access
check still refuses. The refusal names `metastore`.`humankey`.invoices, without the `lightning` prefix and
the `northwind` model, while the grants are stored as `LIGHTNING.METASTORE.HUMANKEY.NORTHWIND.*`, so the
two identifiers may simply never match. Another team reported the same message in the help channel. Until
it is fixed our agents read the USL with the builder login, and the write guard plus the key approval stay
the controls that matter; switching to the agent user is a credentials change.

## Reflection

**First impression.** I had not used a platform like this before. I had a feeling something like it
should exist, because the gap was there in the market. Installing the local edition was easy and the
guide was enough.

**How it saved time.** Without Zetaris, each check would need its own connector code for Postgres and
for the GLEIF API, plus our own join, retry and caching logic. With it, the GLEIF API is a table, the
ERP is a table, and the registry check is one `SELECT` on the USL's `vendors`. In numbers:
- GLEIF as a source: 4 statements (`scripts/register_zetaris_sources.sql`), no HTTP, paging or JSON code of ours.
  Most of the effort was finding real LEIs for the vendors.
- Data quality: 6 rules, each one line (5 `REGISTER DQ` expressions in `scripts/setup_zetaris.py` plus the
  `invoices.vendor_id` foreign key declared in the USL model).
- The count witness that the hardware key signs comes from one `SHOW DQ INVALID RECORD` query per run. It
  replaced the anti-join and count-comparison code we would otherwise have written and tested ourselves for
  "is every invoice's vendor known?", the check whose silent failure (an inner join dropping the invoice)
  is exactly what an invoice fraud would hide behind.

**How it helps in this kind of work.** Accounts payable fraud checks are cross-system questions: the
ERP says what we expect, the registry says who the company really is, the payment history says where
money actually went. A semantic layer lets an auditor and an agent ask the same question in the same
words, and the DQ results are a standing control that does not depend on the agent remembering to check.

**Where I would use it.** Mobile apps almost always keep their data in several places. Apps that handle
money (invoices, wallets, bookings) have it hardest: orders live in the app's own database, payments in
Google Play or a payment gateway, and the real money in the bank statement. The important question always
sits between them: which payment does not match its order? In my own projects I need exactly this kind of
data integration, and it is what the agents in this project do, with evidence.

**What we would improve** (from building this, offered constructively):
- The one I hit myself: I created a non-administrator user for the agents and granted it read access to
  the USL. Zetaris accepted the grant and lists it, but the user still cannot read the USL (section 5).
  Once that works, agents can run on a read-only identity, as your permissions guide recommends.
- `SHOW DQ INVALID RECORD` is the most useful command for agents. A form that returns only the keys
  (or a count by key) would make it cheap to call on every run.
- `COMPILE USL` needs each `CREATE TABLE` on its own line; a client that normalises whitespace gets
  "Invalid DDL statement". A clearer error, or accepting `;` as the only separator, would help.
- `DESCRIBE BY` text rejects parentheses and some punctuation; the error could name the bad character.
- A REST table re-calls the API on every query. Measured on our GLEIF view (local install, 12 rows, 3 runs
  each, 24 Oct): about 1.3 s per query uncached; `CACHE TABLE gleif.lei_entities` brought it to about 0.2 s
  with identical rows. But that cache has no expiry and does not survive a restart. The documented TTL,
  `OFFSITE CACHE TABLE gleif_rest.lei_records TO MEMORY WITH (expireInSec "900")`, returns "Cache is not
  supported for this data source" for a Lightning REST table. An `expireInSec` for REST tables (or for
  `CACHE TABLE`) would make federated checks with public APIs fast without serving stale registry data
  forever. We left caching off in HumanKey: the critic re-runs every query to check it, and a cached
  re-run would match trivially.
- `SHOW TABLES` being disabled in favour of `SHOW NAMESPACES OR TABLES IN …` surprised our first
  script; a hint in the error message pointing to the new form would save time.
